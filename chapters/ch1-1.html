渐进式加载网页图片

可视化的第一步不是画图,而是把内容又快又稳地送到用户眼前。 本章以"图片如何加载"为切口,理解渐进式渲染、骨架屏、懒加载三大手段, 以及衡量它们效果的两个核心指标 LCP 与 CLS。

HTML 基础性能优化用户体验

🎯 学习目标

  • 能说出渐进式渲染、骨架屏、懒加载分别解决什么问题
  • 掌握 <img> 的 loading / decoding / 尺寸属性的正确写法
  • 会用 IntersectionObserver 实现自己的懒加载逻辑
  • 理解 LCP、CLS 两个 Web 性能指标与加载策略的关系
KP 1.1

渐进式渲染:先模糊,后清晰

浏览器下载一张大图需要时间。线性(基线)JPEG 从上到下逐行传输—— 用户先看到图片的上半截;而渐进式(Progressive)JPEG 先传一张极低分辨率的整图, 再逐步细化,用户几乎立刻就能看到"大概的样子"。

两者的总下载量几乎相同,差别只在字节的组织顺序。 但心理学上,"0.5 秒看到模糊全图"远比"2 秒后突然出现清晰图"体验更好—— 用户更早建立预期,等待焦虑显著降低。

💡 为什么可视化课程先讲这个?图表的本质也是"渐进理解": 先让读者看到整体形状(趋势、异常),再引导关注细节。加载策略与视觉设计遵循同一条认知规律。
  • 基线式:自上而下逐行显示,信息不完整,易造成误读(只看到半张图)
  • 渐进式:低清 → 高清,用户越早"看全",越早开始理解
img-progressive.html
<!-- 同一张图,服务端提供渐进式编码版本 -->
<img src="chart-progressive.jpg"
     alt="2024 年销量图表"
     width="800" height="600">

<!-- Photoshop / libjpeg 导出时勾选 Progressive 即可,
     体积通常还比基线式小 5%~10% -->

KP 1.2

骨架屏:提前剧透布局

图片加载前页面往往是一块空白;图片到达后内容突然下移,页面"跳一下"。 骨架屏(Skeleton Screen)用灰色的占位块提前勾画出即将出现的内容布局: 头像是圆的、标题在左边、图片是 16:9——用户不需要看到内容,就已经知道内容会出现在哪里。

关键收益有二:其一,消除布局跳动,改善 CLS(见 1.4);其二, "系统正在工作"的信号降低了用户的等待挫败感——这比转圈加载动画更安静、更克制。

  • 骨架块的形状、比例必须与真实内容一致,否则骨架本身就是一次布局欺骗
  • 配合微弱的"呼吸"动画(shimmer),提示加载仍在进行
  • 数据到达后,骨架 → 内容的替换要平滑(opacity 过渡),不要闪烁
skeleton.css
/* 骨架块:灰色圆角 + 横向流光 */
.skeleton {
  background: linear-gradient(90deg, #e8ecf2 25%, #f5f7fa 50%, #e8ecf2 75%);
  background-size: 400px 100%;      /* 让渐变可被平移 */
  animation: shimmer 1.2s infinite linear;
  border-radius: 6px;
}
@keyframes shimmer {
  0%   { background-position: -200px 0; }
  100% { background-position:  200px 0; }
}

/* 数据到达后:骨架淡出、内容淡入,避免闪烁 */
.skeleton { transition: opacity .3s; }
.loaded   { animation: none; opacity: 0; }

KP 1.3

懒加载:看不见的,先不加载

一个相册页面可能有一百张图,但视口里一次只显示五六张。 懒加载(Lazy Loading) 的策略是:视口外的图片先不请求, 快滚动到时再加载。首屏请求数与流量立刻下降,LCP 自然改善。

现代浏览器一行属性即可启用:loading="lazy"。 若需要更精细的控制(提前量、加载占位、数据上报),可以用 IntersectionObserver 自己实现——它是浏览器原生的"元素进入视口"观察器, 比 scroll 事件监听性能好得多(不阻塞主线程、自动合批回调)。

⚠️ 懒加载不是万金油:首屏图片不要懒加载(反而延迟了 LCP),只对视口外、且用户可能滚动到的内容启用。
lazy.js
// 方式一:原生懒加载,一行搞定
<img src="pic.jpg" loading="lazy" decoding="async" width="800" height="600">

// 方式二:IntersectionObserver 自定义懒加载
const io = new IntersectionObserver((entries) => {
  entries.forEach((entry) => {
    if (!entry.isIntersecting) return;    // 还没进入视口
    const img = entry.target;
    img.src = img.dataset.src;            // 真实地址藏在 data-src 里
    io.unobserve(img);                    // 加载一次后停止观察
  });
}, { rootMargin: "200px" });              // 提前 200px 开始加载

document.querySelectorAll("img[data-src]").forEach((img) => io.observe(img));

KP 1.4

LCP 与 CLS:给体验打分

优化不能靠感觉,需要指标。Web 性能的两个核心指标与本章内容直接相关:

  • LCP(Largest Contentful Paint,最大内容绘制):视口内最大元素渲染完成的时间。渐进式渲染、懒加载、首屏精简都在优化它。
  • CLS(Cumulative Layout Shift,累积布局偏移):页面生命周期内所有"意外布局跳动"的总分。骨架屏、为图片预留宽高都是为了它。

最典型的 CLS 杀手:<img> 不写 width/height。 图片到达前高度为 0,到达后把下方内容整体推下去——用户正要点按钮,按钮跑了。 浏览器其实只需提前知道宽高比就能预留空间。

cls-fix.html
<!-- ❌ 坏:没有尺寸,图片到达时布局下移,CLS +0.42 -->
<img src="chart.jpg" alt="销量图表">

<!-- ✅ 好:浏览器预留 800×600 的盒子,零偏移 -->
<img src="chart.jpg" alt="销量图表" width="800" height="600">

<!-- 响应式布局下用 CSS 锁定宽高比,同样有效 -->
<style>
  .figure { aspect-ratio: 4 / 3; }   /* 宽高比 4:3,高度永远算得出 */
</style>
